# 로컬 기록으로 문맥 관리 비용을 비교하는 절차

먼저 실제 기록의 사용량을 합산하고, 그 기록의 작업량을 고정한 채 압축·노트·원문 재입력 비용을 바꿔 계산해요. 비싼 모델을 다시 호출하지 않고 후보를 줄일 수 있어요. 다만 아직 실행하지 않은 방식에서 모델이 과거 원문을 얼마나 읽을지는 기록만으로 알아낼 수 없어요. 그 부분은 범위를 넣어 비교하고, 마지막에 적은 실제 실행으로 보정해요.

이번 압축 파일에는 실행 가능한 오프라인 도구도 들어 있어요. 도구는 네트워크나 모델을 호출하지 않고, 원본 세션 파일을 수정하지 않아요.

2026-09-06 16:10 KST 로컬 실측은 `docs/context-cost-local-measurement.md`에 있어요. 기본 설정에서는 새 노트 방식과 기존 압축이 또이또이해요. 이 안내의 합성 예제 금액이나 가정 격자를 그 실측 결론으로 바꾸어 읽지 않아요.

## 1. 무엇을 비교할지 먼저 고정해요

첫 질문은 같은 모델·같은 작업량에서 기존 방식과 노트 방식의 **입력·출력 비용 합계가 얼마인지**예요. 캐시 적중률 자체를 목표로 삼지 않아요. 모델별로 따로 계산해요.

아스트라는 사용자 설정대로 물리적 창 272,000을 유지해요. 기존 방식 기준점은 약 244,800이고, 새 방식에도 같은 목표를 지정한 비교를 먼저 해요. 272,000을 넘는 계산은 유효한 실행으로 취급하지 않으므로 이 실험에 장문 할증을 넣지 않아요. 다른 물리적 창으로 바꾼 별도 실험에서만 가격 구간을 다시 적용해요.

페이블은 현재 1,000,000 창과 서버 압축 650,000 지점을 기준으로 삼되, 100,000·150,000·200,000·250,000·300,000·400,000·500,000·650,000·800,000을 비교해요. 각각 10·15·20·25·30·40·50·65·80%예요. 한 세션에서 임계점을 계속 바꾸지 않고, 같은 기록을 각 후보로 독립 재생해요.

기존 방식이 무엇인지도 확인해요. 루바토의 페이블 서버 압축, 센피의 OpenAI 원격 압축, 일반 클라이언트 요약을 한 종류로 합치지 않아요. 특히 OpenAI의 불투명한 압축 항목은 저장 문자열 길이가 실제 모델 입력 토큰 수와 같지 않아요.

비교 방식은 두 가지로 분리해요.

- **같은 지점 비교:** 두 방식이 같은 입력 목표에서 창을 바꾸게 해요. 기억을 이어주는 방식 자체의 비용을 비교해요.
- **각 방식의 임계점 비교:** 같은 작업 기록에서 각 방식의 목표를 따로 바꿔요. 어떤 설정 구간이 비교적 저렴한지 찾아요.
- **실제 기본값 비교:** 기존 실제 설정과 새 방식의 기본 80%를 비교해요. 이 차이에는 알고리즘뿐 아니라 임계점 차이도 포함된다고 적어요.

## 2. 가격과 사용량을 섞지 않아요

가격 설정은 `docs/context-cost-prices.json`에 있어요. 2026-09-06에 확인한 표준 사용량 과금 가격을 시작값으로 넣었어요. 실행 때 적용되는 계약·중계 수수료·우선 처리 요율이 다르면 설정을 바꿔요.

| 모델 | 일반 입력 / 100만 | 캐시 읽기 / 100만 | 캐시 쓰기 / 100만 | 출력 / 100만 |
|---|---:|---:|---:|---:|
| 아스트라 | $10 | $1 | $12.50 | $50 |
| 페이블 5.1 | $10 | $0.25 | 5분 $12.50 / 1시간 $20 | $50 |

아스트라도 캐시 쓰기 요금을 빼면 안 돼요. 페이블의 1/40 할인은 읽기에 해당해요. 노트를 작성할 때 발생한 출력과, 새 창에서 그 노트를 입력으로 읽는 비용은 서로 다른 항목이에요. 한 번 읽은 원문이 이후 같은 창의 요청에 계속 붙으면 그 후속 읽기도 누적해요.

정규화된 사용량의 계산식은 아래와 같아요. `cacheWrite1h`는 `cacheWrite`의 부분집합이에요.

```text
일반 입력 비용 = input × 일반 입력 단가
캐시 읽기 비용 = cacheRead × 캐시 읽기 단가
캐시 쓰기 비용 = (cacheWrite - cacheWrite1h) × 기본 쓰기 단가
                 + cacheWrite1h × 1시간 쓰기 단가
출력 비용 = output × 출력 단가
합계 = 위 네 비용의 합 / 1,000,000
```

이 도구의 `input`은 캐시를 제외한 일반 입력이에요. 원시 OpenAI 응답처럼 전체 입력을 뜻하는 필드를 그대로 넣지 않아요. 실제 어댑터가 캐시 읽기·쓰기를 빼고 정규화했는지 확인해요. 과거 어댑터가 캐시 쓰기를 기록하지 않고 0으로 채웠다면 그 0은 “실제로 쓰기 비용이 없었다”는 증거가 아니에요.

`output`에 추론 토큰이 포함돼 있으면 `reasoning`을 다시 더하지 않아요. 반대로 눈에 보이는 요약 2천 토큰이 총 청구 출력도 2천이라는 뜻은 아니에요. 도구 인수와 비공개 추론을 포함한 실제 사용량을 사용해요.

구독으로 접속한 코덱스·클로드는 이 금액을 **API 가격으로 환산한 사용량 비용**으로 읽어요. 월 구독료 절감이나 주간 한도 소진율로 바로 변환하지 않아요. 구독 한도에 대한 비공개 산식은 이 도구가 알아내지 못해요.

## 3. 실제 세션의 원가를 먼저 확인해요

실행 중인 파일 대신 루바토가 해당 세션 기록을 더 쓰지 않는 상태에서 복사한 파일을 사용해요. 데이터베이스가 아니라 세션 JSONL 원본이에요. 실행 중인 파일의 마지막 줄만 잘라내서 정상 기록처럼 만들지 않아요.

```sh
# 저장소 루트에서 실행해요. 아래 원본 위치는 실제 세션 파일로 바꿔요.
mkdir -p "$HOME/rubato-cost-work"
chmod 700 "$HOME/rubato-cost-work"
cp /실제/세션/경로/session.jsonl "$HOME/rubato-cost-work/fable-baseline.jsonl"
chmod 600 "$HOME/rubato-cost-work/fable-baseline.jsonl"

node harness/rubato-pi/scripts/context-cost-audit.mjs \
  "$HOME/rubato-cost-work/fable-baseline.jsonl" \
  anthropic/claude-fable-5-1 \
  docs/context-cost-prices.json \
  "$HOME/rubato-cost-work/fable-baseline"
```

아스트라는 모델 인수를 `openai-codex/gpt-6-astra` 또는 실제 기록의 `openai/gpt-6-astra`로 바꿔요. 도구가 가격표와 다른 모델을 자동으로 대체하지 않아요.

출력은 두 개예요.

| 파일 | 의미 |
|---|---|
| `*.audit.json` | 현재 선택된 가지에 기록된 사용량, 별도 압축 사용량, 요약 크기 정보, 누락 경고를 합산해요. |
| `*.trace.json` | 대화 본문 없이 요청 간 새 토큰 추정량·출력 사용량·시간 간격을 내보내요. 가상 재생의 입력이에요. |

이미 존재하는 출력은 덮어쓰지 않아요. 새 출력 이름을 지정해요. 기본은 파일의 마지막 항목에서 부모 연결을 따라간 가지예요. 화면에서 선택한 가지 끝이 다르면 명령 마지막 인수로 `LEAF_ID`를 지정해요. 형제 가지를 동시에 이어 붙이지 않아요.

최초 버전 도구는 **한 모델만 사용한 가지**를 받게 제한했어요. 모델 전환·우선 처리 별칭·공급자 전환이 섞이면 중단해요. 같은 이름이라고 추정해 가격을 붙이지 말고, 같은 모델을 쓴 세션을 고르거나 로컬 개발 에이전트가 명시적 매핑으로 구간을 정규화해야 해요.

### 서버 압축의 중복 계산을 피해야 해요

현재 루바토의 앤트로픽 어댑터는 정상 응답 사용량과 `usage.compaction`을 구분하지만, `usage.cost.total`에는 압축 비용을 이미 더해요. 도구는 정상 토큰과 중첩 압축 토큰을 한 번씩 계산하고, `cost.total`을 또 더하지 않아요. 같은 요약을 화면에 투영한 `anthropic-server-compaction` 경계 항목도 재과금하지 않아요.

일반 압축 항목에 별도 `usage`가 있으면 계산해요. 없으면 0원으로 확정하지 않고 누락으로 표시해요. 원시 서버의 `usage.iterations` 형식은 이 도구가 자동 해석하지 않아요. 서버 응답 원형을 사용하는 로컬 수집기는 모든 반복을 합산하되, 상위 필드와 같은 반복을 중복으로 더하지 않아야 해요.

전송 실패, 내부 재시도, 별도 작업자, 장기기억 생성·검색, 세션 제목 생성, 외부 도구 요금이 이 파일에 전부 남는다고 가정하지 않아요. 실제 청구 대시보드와 맞지 않는 차이는 별도 미계상 항목으로 남겨요. 이 합산은 세션에 기록된 식별 가능한 비용이에요.

## 4. 기록의 추정값을 보정해요

`trace`의 `newTokens`는 기본적으로 UTF-8 바이트를 3으로 나눈 근삿값이에요. 실제 모델의 토큰 수가 아니에요. 한국어·코드·이미지·추론 재전송에 따라 다를 수 있어요. 출력 토큰은 정상 기록에서는 사용량 필드를 사용하지만, 그 필드가 없으면 본문 추정이라고 표시해요.

가능하면 기존 로컬 요청 수집 자료에서 다음 값을 확보해요. 이미 있는 자료를 우선 쓰고, 이 단계 때문에 비싼 장기 세션을 새로 돌리지 않아요.

| 값 | 사용 목적 |
|---|---|
| 공급자에게 실제 보낸 입력의 토큰 수 | 추정 증가량과 고정 지침 크기를 보정해요. |
| 일반 입력·캐시 읽기·캐시 쓰기·출력 | 실제 경로의 비용 합산과 캐시 가정을 검증해요. |
| 모델 요청의 시작·끝 시각 | 기록 시각과 다른 대기 시간을 분리해요. |
| 압축 요청의 입력·출력 사용량 | 캐시가 유지된 요약과 캐시가 끊긴 요약을 구분해요. |
| 압축 후 실제 입력 크기 | 요약과 최근 대화가 얼마나 남는지 보정해요. |
| 노트와 원문 도구 호출 결과 크기 | 새 방식의 추가 입력을 계산해요. |

수동으로 정규화한 `trace`는 `formatVersion: 1`, `calls` 배열을 사용해요. 각 항목은 `newTokens`, `outputTokens`, `gapMs`예요. `newTokens`에는 **이전 응답 중 다음 입력에 실제로 다시 들어가는 부분 + 이번에 새로 들어온 사용자·도구 내용**을 넣어요. 이번 호출이 아직 생성하지 않은 출력을 입력 증가량으로 미리 넣지 않아요. 공급자별로 다시 보내지 않는 추론은 제외해요.

기존 압축을 없앤 가상 재생을 하기 위해 요약 본문 자체는 작업 증가량에 다시 넣지 않아요. 대신 압축 후 남는 크기를 별도 설정으로 지정해요. 여러 부분이 한 기록으로 합쳐져 요청 경계를 복원할 수 없으면 그 세션은 정밀 비교에 사용하지 않아요.

현재 노트 방식 기록은 비용 합산은 가능하지만, 관리용 호출을 일반 작업과 혼동하지 않도록 가상 재생용 `calls`를 비워 반환해요. 기존 방식 기록을 기준 작업으로 사용하거나 관리 호출을 정확히 분리한 자료를 별도로 만들어요.

## 5. 모델 호출 없이 임계점과 원문 읽기량을 바꿔 계산해요

```sh
node harness/rubato-pi/scripts/context-cost-simulate.mjs \
  "$HOME/rubato-cost-work/fable-baseline.trace.json" \
  docs/context-cost-fable-scenarios.json \
  "$HOME/rubato-cost-work/fable-grid.json"

node harness/rubato-pi/scripts/context-cost-simulate.mjs \
  "$HOME/rubato-cost-work/astra-baseline.trace.json" \
  docs/context-cost-astra-scenarios.json \
  "$HOME/rubato-cost-work/astra-grid.json"
```

가격은 시나리오 파일의 `prices`에도 들어 있어요. 가격표를 고쳤으면 시나리오 파일의 가격도 함께 고쳐요. 시나리오마다 전체 가정이 결과에 남아요. 다른 모델 기록에 가격만 바꿔 적용하면 경고를 남겨요. 그것을 대상 모델의 실제 행동·토큰 수라고 해석하지 않아요.

로컬 기록을 준비하기 전 명령만 확인하려면 `docs/context-cost-example-trace.json`을 사용할 수 있어요. 이 파일은 만든 가상 자료이므로 결과의 최저점을 운영 설정으로 사용하지 않아요.

### 기본 시나리오가 계산하는 항목

| 항목 | 기본값 | 의미 |
|---|---:|---|
| 고정 지침·기존 도구 | 8,000토큰 | 실제 로컬 값으로 바꿔야 해요. |
| 새 방식의 추가 도구·지침 | 1,200토큰 | 두 방식의 도구 정의 크기를 같다고 처리하지 않아요. |
| 기존 요약의 유지 크기 | 5,000토큰 | 재입력되는 크기예요. |
| 기존 요약의 청구 출력 | 5,000토큰 | 유지 크기와 별도 변수예요. 추론 포함 사용량으로 바꿔요. |
| 유지되는 최근 원문 | 0토큰 | 기존 방식에 유리한 단순 기준이에요. 실제 유지량으로 보정해요. |
| 노트의 유지 크기 / 청구 출력 | 각각 2,000토큰 | 보이는 노트와 실제 생성 비용은 달라질 수 있어요. |
| 노트 생성 이후 기존 큰 창의 추가 왕복 | 1회 | 0원 전환이라고 긴 입력 비용을 빼지 않아요. |
| 새 창의 노트 읽기 | 1회 | 과거 원문 검색이 0회여도 이 비용은 들어가요. |
| 추가 과거 원문 | 창마다 0·5·10·20·50·100K | 노트 본문과 별개예요. |
| 원문 검색·읽기 호출 수 | 기본 10K당 1회 올림 | 실제 검색→읽기가 두 번이면 호출 수도 늘려요. |
| 캐시 유효 시간 | 아스트라 30분 / 페이블 5분 | API 문서·선택한 정책 기준의 시작값이에요. 중계 경로에서 다시 확인해요. |

기존 요약 입력이 모두 캐시로 읽히는 경우와 모두 새로 쓰이는 경우를 따로 계산해요. 실제는 사이일 수 있으므로 `summaryCacheHitFraction`을 관측값으로 바꿔요. 노트·원문 조회는 도구 결과 텍스트 비용뿐 아니라 그 결과를 얻기 위한 모델 왕복의 현재 입력·출력도 계산해요.

현재 도구는 원문을 새 창 초반에 읽는 시나리오예요. 늦게 읽는 경우보다 가져온 원문이 이후 더 많은 요청에 남지만, 초반의 검색 요청 자체는 입력이 더 작아요. 따라서 이것을 일방적인 상한·하한으로 부르지 않아요. 읽는 시점까지 구분할 자료가 생기면 로컬 개발 에이전트가 호출별 조회 일정을 넣어 확장해도 돼요.

기존 방식에서도 요약에 빠진 내용을 파일·기억·기록에서 다시 찾는다면 `summaryRetrievalTokens`와 `summaryRetrievalCalls`를 지정해요. 기존 방식은 항상 무료로 모든 정보를 복구한다고 가정하지 않아요.

### 비용식의 중요한 차이

새 방식은 다음 항목의 합이에요.

```text
일반 작업의 입력·출력
+ 현재 큰 문맥에서 노트 생성
+ 노트 저장 후 전환을 요청하는 추가 왕복
+ 새 창의 작은 안내와 노트 읽기
+ 과거 기록을 찾는 모델 왕복과 결과의 신규 입력
+ 가져온 내용이 남은 요청들에서 다시 읽히는 비용
```

기존 방식은 다음 항목의 합이에요.

```text
일반 작업의 입력·출력
+ 해당 연결 방식의 압축 생성 요청
+ 압축 후 요약·최근 원문을 다시 입력하는 비용
+ 그 내용을 이후 요청들에서 다시 읽는 비용
+ 필요한 경우 추가 복구 비용
```

시뮬레이터는 작업 요청 수와 그 출력량을 모든 후보에서 고정해요. 창을 세 번 넘겼다는 이유로 같은 작업량이라고 간주하지 않아요. 기록 끝에서 쓸모없는 마지막 압축을 강제로 한 번 더 하지 않아요. 너무 작은 창에 노트·다음 작업이 들어가지 않으면 억지로 잘라 계산하지 않고 해당 후보를 무효로 표시해요.

## 6. 캐시와 시간 가정을 실제 환경에 맞춰요

이 도구의 캐시 재사용은 공급자 캐시를 그대로 재현한 것이 아니라 토큰 단위 가정이에요. `cacheHitFraction`, `summaryCacheHitFraction`, `staticReuseFraction`, `cacheTtlMs`, `writeMisses`를 결과와 함께 남겨요. 기본은 재사용 가능한 이전 입력을 모두 읽고 새 부분은 캐시에 쓰는 단순 모델이에요.

OpenAI 최신 계열은 명시적·암묵적 캐시 경계와 키가 중요해요. 문자열의 앞부분이 같다는 이유만으로 항상 그 길이만큼 캐시에 적중하지 않아요. 루바토의 실제 직접·코덱스 연결이 어떤 키·경계를 보내는지와 응답의 사용량을 확인해야 해요. 이 패치는 중계 연결의 캐시 정책을 임의로 바꾸지 않아요.

별도의 감도 비교를 해요.

- 작업 증가량: `growthMultiplier`를 0.7·1.0·1.3으로 바꿔 토큰 추정 오차를 봐요. 이 범위가 통계적 신뢰구간이라는 뜻은 아니에요.
- 기억 유지량: 요약 3·5·10K, 노트 1·2·5K, 최근 원문은 관측값을 중심으로 바꿔요. 청구 출력은 유지량과 분리해요.
- 왕복 횟수: `checkpointExtraCalls`를 0·1·2로 바꾸고, 노트·원문 읽기 요청 수도 따로 바꿔요.
- 캐시와 대기: 실제 시간 간격, 캐시가 만료된 경우, 고정 지침 재사용 실패, 1시간 쓰기 정책을 각각 비교해요.

페이블 1시간 쓰기를 계산할 때는 `cacheWrite1h: true`뿐 아니라 `cacheTtlMs: 3600000`도 지정해요. 아스트라에 지원되지 않는 캐시 기간을 임의로 넣어 실제 정책이라고 부르지 않아요. 공급자별 최소 캐시 길이·블록 단위·이미지 처리·전송 재시도까지 이 간단한 계산기가 완전히 모사하는 것은 아니에요.

## 7. 결과에서 후보를 고르는 방법

`totalCostUSD`를 같은 모델·같은 기록·같은 기억 가정끼리 비교해요. `productiveCalls`는 같아야 해요. `transitions`, `totalCalls`, `cacheReadTokens`, `cacheWriteTokens`, `outputTokens`, `costByKind`를 함께 봐요. 원문을 안 읽은 시나리오의 최저가와 100K를 읽는 시나리오의 기존 방식을 섞어 승자를 고르지 않아요.

최저점 하나보다 **가정을 바꿔도 크게 손해 보지 않는 구간**을 찾아요. 추천 절차는 다음과 같아요.

1. 한 기록의 최저점을 바로 채택하지 말고 여러 길이의 실제 세션에서 계산해요.
2. 페이블 기존 방식은 65%를 고정 기준으로 남겨 다른 임계점의 절약액·절약률을 나란히 봐요.
3. 두 방식은 같은 지점에서 먼저 비교하고, 이후 각 방식의 유리한 임계점 범위를 비교해요.
4. 원문 읽기량과 왕복을 늘려도 새 방식이 이기는 범위, 반대로 기존 방식이 이기는 범위를 정리해요.
5. 그 범위가 실제로 가능한지 모르면 “비용 우위 미결정”으로 남기고 다음 행동검증의 측정 목표로 삼아요.

기억 방식이 바뀌면 과거 검색 빈도와 재작업도 바뀌므로, 가상 재생은 조건부 비교예요. 로컬 기록만으로 실제 새 방식의 원문 읽기량을 확정하지 못해요. 작업 품질을 완전히 무시하면 정보를 읽지 않는 정책이 가장 싸게 나올 수 있지만, 그것을 성공적인 대체 구현이라고 부르지는 않아요.

권장 결과물은 아래 다섯 가지예요.

- 모델·연결·가격 버전·기록 식별자·가지를 적은 실험 설명서
- 관측 사용량 합산과 누락 항목 표
- 모델별 임계점·원문 읽기 가정별 비용표
- 최저점 근처의 안정적인 후보 1~2개와 아직 모르는 값
- 다음 행동검증에서 측정할 노트 크기·원문량·왕복·성공 조건

## 8. 다음 실제 실행으로 넘기는 기준

설치본 검사와 모델 없는 전환 검증을 먼저 끝내요. 그 뒤 저렴한 모델로 도구·전환·복구가 동작하는지만 확인할 수 있어요. 그 모델의 검색 횟수를 페이블·아스트라의 검색 횟수로 그대로 대입하지 않아요.

마지막에는 선택한 후보만 실제 대상 모델에서 짧게 실행해 노트 청구 출력, 큰 문맥 추가 왕복, 새 창 원문 읽기량과 캐시 사용량을 수집해요. 이 자료로 가정을 보정한 뒤 다시 오프라인 계산해요. 상세 절차는 `docs/context-notes-behavior-guide.md`에 있어요.

이번 문서는 페이블 65%를 새 기본값으로 유지해야 한다거나 25%로 바꿔야 한다고 확정하지 않아요. 이전 대화에서 제시한 최적점 숫자도 재사용하지 않아요. 실제 자료로 보정한 계산 결과가 나온 뒤 설정을 정해요.
