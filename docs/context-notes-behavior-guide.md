# 비용 후보를 고른 뒤 행동과 복구를 검증하는 절차

돈이 덜 드는 후보가 나와도 실제 작업을 잇지 못하면 채택하지 않아요. 먼저 모델 없는 설치·전환 검증으로 구현 문제를 제거하고, 그다음 모델이 노트와 원문을 실제로 사용하는지 확인해요. 비싼 대상 모델은 후보 1~2개를 좁힌 뒤 사용해요.

## 1. 세 종류의 검사를 구분해요

| 단계 | 목적 | 대상 모델 호출 |
|---|---|---|
| 설치본·시험용 응답 검사 | 저장·전환·취소·다시 열기의 구현 오류를 잡아요. | 없어요. |
| 저렴한 모델의 작은 작업 | 도구 이름·노트 지침·원문 참조를 이해하는지 확인해요. | 선택한 저렴한 모델만 사용해요. |
| 아스트라·페이블 후보 확인 | 실제 원문 읽기량, 큰 창 왕복, 과금 사용량과 작업 성공을 보정해요. | 최종 후보만 사용해요. |

저렴한 모델의 성공은 대상 모델의 품질·검색 횟수·비용을 보증하지 않아요. 두세 번의 대상 모델 실행도 일반적인 성공률을 확정하는 통계 검증은 아니에요. 최초 도입의 실패를 찾고 비용 가정을 보정하는 자료로 사용해요.

## 2. 모델을 호출하기 전에 실행할 검사

저장소 루트에서 실행해요. 루바토가 요구하는 Node 24 이상과 고정 의존성이 있어야 해요.

```sh
npm --prefix harness/rubato-pi run check:context-notes-engine
npm --prefix harness/rubato-pi run test:context-notes
npm --prefix harness/rubato-pi run test:context-cost
RUBATO_CONTEXT_MODE=summary npm --prefix harness/rubato-pi run test:context-notes

RUBATO_TEST_CONTEXT_NOTES_ENGINE=1 \
  node --test harness/rubato-pi/test/integration/context-notes-engine.test.mjs
```

마지막 검사는 실제 SessionManager의 저장·문맥 구성·재열기를 검사해요. 시험용 `applyCompaction` 연결을 사용하므로 전체 AgentSession 반복 실행 검사라고 부르지 않아요. 플래그를 생략하면 건너뛰므로 그 결과를 통과로 계산하지 않아요.

이후 로컬 개발 에이전트는 **실제 AgentSession + 시험용 모델 응답**으로 통합 검사를 추가·실행해요. 기존 `harness/rubato-pi/test/helpers/mock-openai.mjs`와 공급자 요청 수집 관례를 먼저 확인해 재사용해요. 새 비공개 통신 형식을 추측해 구현하지 않아요.

시험용 응답은 순서대로 `notes_write_file`, `new_context`, `notes_read_file`, `history_search_contents`, `history_read_item`을 호출하게 해요. 생성 텍스트의 품질은 검사하지 않고 아래 사실을 자동 단언해요.

1. 노트 쓰기 성공이 모델에 전달되기 전에 원문 세션 파일에 노트가 있어야 해요.
2. `new_context`는 도구 실행 중간에 현재 입력을 지우지 않고 묶음이 끝나면 적용해야 해요.
3. 전환 후 첫 공급자 요청에는 새 창 안내만 있고, 이전 전체 대화나 노트 본문은 없어야 해요. 고정 지침·도구 정의는 유지해요.
4. 노트 읽기와 원문 읽기 결과는 명시적 호출 뒤에만 입력에 추가돼야 해요.
5. 다음 창 전환이나 세션 이동이 없는 연속 요청은 이전에 보낸 안내와 메시지를 중간에서 바꾸지 않아야 해요.
6. 기존 요약 생성·원격 압축·서버 압축 요청이 한 번도 호출되지 않아야 해요.

공급자에 넘기기 직전의 요청을 수집해요. 내부 `context` 이벤트 결과만 보면 그 뒤 변환이 과거 대화를 다시 넣는 문제를 놓칠 수 있어요. 고정 지침의 변경 여부, 도구 목록·순서, 캐시 키·경계·사용량도 함께 확인해요. 요청의 앞부분이 같다는 검사와 서버의 실제 캐시 적중은 다른 검사예요.

## 3. 저장·경합·오류 주입 검사

실제 작업 폴더와 분리한 임시 폴더에서 검사해요. 실패를 넣는 대상은 시험용 파일과 세션으로 제한해요.

| 상황 | 기대 결과 |
|---|---|
| 노트 저장 뒤 새로운 사용자 요구사항 도착 | 오래된 노트로 전환하지 않아요. 새 요구사항이 남아 있어야 해요. |
| 같은 도구 묶음에서 노트 저장 후 파일 변경 결과가 늦게 도착 | 그 결과를 반영한 노트가 없으면 전환하지 않아요. |
| 엔진이 비동기 검사 중일 때 새 입력 도착 | 실제 경계 저장 직전 검사에서 거부해요. |
| 저장 전 디스크 쓰기·동기화 실패 | 노트 성공을 반환하거나 과거 문맥을 버리지 않아요. |
| 경계 저장 뒤 후처리 실패 | 실행을 중단하고, 두 번째 경계를 만들지 않아요. 같은 세션을 다시 열어 복구해요. |
| 사용자 취소·모델 오류 | 예약된 전환으로 자동 작업 재개를 하지 않아요. |
| 프로세스 종료 후 재열기 | 같은 창 번호·식별자와 현재 가지의 노트를 복원해요. |
| 종료 후 검색 데이터베이스를 백업하고 재생성 | 세션 파일만으로 원문과 노트가 복구돼야 해요. |
| 이전 가지로 되돌리기·분기 | 버린 미래 가지의 노트와 원문은 조회되지 않아야 해요. |
| 매우 긴 노트·긴 한 줄·유니코드·여러 검색 페이지 | 잘린 범위를 확인하고 다음 위치부터 읽을 수 있어야 해요. |
| 기존 원격 압축 경계가 있는 세션에서 새 창으로 전환 | 이전 원격 압축 항목이 최종 요청에 다시 삽입되지 않아야 해요. |
| 이미지 원문 재주입 | 지원 크기·형식은 모델에게 실제 이미지로 전달되고, 지원하지 않으면 오류가 보여야 해요. |
| 장기 실행 작업과 대기 입력이 있는 전환 | 파일·작업 식별자는 유지되고 입력이 유실·중복 실행되지 않아야 해요. |

Node 24 설치본에서 필수 변환이 실패하면 검사를 무시하지 않아요. 기준 위치가 실제 코드에서 옮겨진 정도라면 같은 의미의 위치로 수정할 수 있어요. 하지만 안전한 도구 묶음 경계가 없어서 구조 자체를 바꿔야 한다면 `DESIGN_REVIEW_REQUEST.md`를 만들고 설계 검토로 돌아가요.

## 4. 작은 행동검증 과제를 만들어요

실제 서비스와 외부 계정을 사용하지 않는 작은 저장소를 복사해요. 먼저 요구사항과 정답을 기계적으로 검사하는 테스트를 작성해요. 같은 과제를 두 모드에 주고 테스트를 바꾸지 않아요.

첫 창에는 세 가지 정보를 넣어요. 첫째는 끝까지 지켜야 할 금지 변경, 둘째는 실패했던 접근과 그 이유, 셋째는 원문에만 남겨야 할 임의 표식이에요. 표식을 노트에 복사하지 말라고 요청해 실제 원문 조회가 필요한 경로를 만들어요. 검사기는 그 표식을 알고 있지만 모델의 다음 창 지침에는 정답을 다시 넣지 않아요.

모델이 작은 코드 변경과 검사를 진행한 뒤 노트를 쓰고 전환하도록 해요. 두 번째 창에서는 이전 금지 변경과 충돌할 수 있는 작업을 요청해요. 세 번째 창에서는 실패했던 접근의 이유와 표식을 확인해야 완료할 수 있는 작업을 줘요. 원래 사용자 요청의 위치를 정확히 읽었는지와 코드 테스트의 결과를 함께 봐요.

자동 합격 기준은 다음과 같아요.

- 코드 테스트와 금지 변경 검사가 처음 요구사항 그대로 통과해요.
- 현재 창에 없던 표식을 실제 원문 도구로 읽어 정확히 복구해요.
- 노트에는 목표·중요 결정·현재 진행·다음 단계와 유효한 원문 위치가 있어요.
- 같은 작업 폴더에서 이어지고, 허가되지 않은 새 작업을 시작하지 않아요.
- 한도·저장·전환 실패를 완료로 보고하지 않아요.

24K 같은 작은 목표는 전환 경로를 빨리 확인하는 용도예요. 그 결과의 검색 횟수나 비용을 250K·650K 운영 환경으로 곧바로 확대하지 않아요. 고정 지침 자체가 작은 목표를 넘으면 실제 크기를 기록하고 목표를 올려요.

## 5. 대상 모델에서 비용 가정을 보정해요

설치·무료 통합·작은 과제가 통과한 뒤에만 실제 아스트라와 페이블을 사용해요. 각 모델의 기존 방식 기준점과 비용 계산으로 고른 새 방식 후보 한 개부터 시작해요. 어느 후보가 더 낫다는 근거가 충분하지 않으면 후보를 많이 돌리는 대신 아직 모르는 변수를 먼저 좁혀요.

아스트라는 272K 물리적 창을 그대로 유지해요. 페이블은 1M을 유지한 상태에서 선택한 임계점만 바꿔요. 기존 페이블 서버 압축의 `trigger.value`와 새 방식 입력 목표는 다른 설정이라는 점을 확인해요. 실제 기존 방식의 임계점 변경은 별도 실험 사본에서만 하고 요청을 수집해 확인해요.

시험 전 **예산 상한, 최대 요청 수, 최대 창 전환 수, 도구 부작용 범위**를 사용자가 승인한 값으로 지정해요. 첫 대상 모델 검사는 경계 한 번의 노트 작성→전환→노트·원문 읽기까지 확인한 뒤 멈춰 비용 기록부터 봐요. 예산이 남는다고 자동으로 다음 장기 실험을 시작하지 않아요.

반드시 다음 자료를 수집해요.

| 자료 | 비용 계산에 반영할 값 |
|---|---|
| 모델·연결·추론 설정·가격 버전 | 서로 다른 실행을 비교하지 않도록 고정해요. |
| 창 전환 전 마지막 요청들 | 노트 생성 요청과 큰 창의 추가 왕복을 구분해요. |
| 노트 쓰기 인수와 응답 사용량 | 노트 유지 크기와 실제 청구 출력을 분리해요. |
| 새 창의 노트·원문 도구 호출 | 검색 횟수, 읽기 횟수, 중복 읽기와 결과 크기를 측정해요. |
| 요청별 입력·캐시 읽기·쓰기·출력 | 새로 들여온 원문이 후속 요청에서 얼마나 반복되는지 확인해요. |
| 완료·오류·취소 상태와 코드 테스트 | 싸지만 작업을 누락한 실행을 승자로 처리하지 않아요. |

`context-notes-report.mjs`는 도구·전환 진단을 보조로 보여줘요. `request_prepared`는 요청 준비 이벤트이며 실제 과금 요청 수가 아니에요. 공급자에 전송한 횟수와 사용량으로 최종 비용을 계산해요. 도구 결과 바이트 수도 토큰 수로 단정하지 않아요.

관측한 크기·왕복·캐시 값을 오프라인 시나리오에 되넣고 다시 계산해요. 비용 추정과 차이가 나면 기록을 고친 뒤 후보를 다시 비교해요. 모델이 원문을 적게 읽었다고 초기 원문 읽기 가정을 다른 모델에도 그대로 적용하지 않아요.

## 6. 채택·보류·설계 재검토

작업을 동등하게 완료한 실행끼리 비용을 비교해요. 한쪽이 오류로 일찍 끝나서 싼 경우는 비용 절감으로 계산하지 않아요. 후보 간 차이가 입력 추정 오차나 캐시 변동보다 작으면 우위를 확정하지 않아요.

작은 이름·형·호출 위치 차이와 테스트 오류는 설계를 유지한 채 로컬 에이전트가 고칠 수 있어요. 같은 세션을 유지할 수 없거나, 실제 엔진에서 안전한 전환 시점을 만들 수 없거나, 선택한 연결이 자체 요약을 강제한다면 임의의 새 세션·별도 요약으로 우회하지 않아요. 문제 위치, 재현, 기대·실제 결과, 실패 이유, 영향 범위, 가능한 대안과 필요한 판단을 적어 설계 검토로 돌려줘요.

터미널과 원격 화면에서 상태·오류·다시 열기 안내까지 실제로 따라가 본 뒤 화면 검증을 완료로 표시해요. 그 전 상태는 개발 산출물에 `IMPLEMENTED, RENDER VERIFICATION PENDING`으로 남겨요.
