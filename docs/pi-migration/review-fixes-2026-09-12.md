# 파이 전환 후 실행·갱신 경로를 보완했어요

점검 기준은 `rubato/base`의 `434fe81be0b86c37a0b2289eecc0977ec84901de`예요. 센파이 전체 삭제나 파이 버전 변경은 이번 범위에 넣지 않았어요. `senpi-pty`와 복귀 경로, `fullRubatoParity: false`는 유지해요.

## 바꾼 동작

- 커서가 파일을 수정할 때 기존 실행 권한을 보존해요. 심볼릭 링크는 원본 대상을 수정하고 링크 자체는 유지해요. 끊어진 링크는 덮어쓰지 않고 실패해요. 같은 대상을 가리키는 링크와 원본은 잠금을 공유해요.
- 커서의 자체 쓰기·수정 실행기를 공통 `executeTool` 경로로 보냈어요. 입력 검사와 실행 전·후 처리를 거치지만, 모델에게 숨긴 쓰기·수정 도구를 다시 노출하지는 않아요. 실행 가능한 함수를 담은 내부 `nativeFileTool` 인자로 연결하며 모델 입력에서 이 인자를 만들지 않아요.
- 설치·갱신은 같은 파일시스템의 별도 디렉터리에서 다운로드와 조립, 검증을 마친 뒤 교체해요. 교체 중 예외가 나면 이전 실행본을 복원해요. 처음 설치하다 실패해도 불완전한 디렉터리를 목적지에 남기지 않아요. 설치·갱신·실행본 복귀는 같은 잠금을 사용해요. 강제 종료나 전원 장애까지 원자적으로 복구한다는 보장은 아니에요.
- 실행과 상태 명령이 같은 엔진 선택 함수를 사용해요. 요청한 엔진과 실제 선택한 엔진, 복귀 여부, 선택한 노드를 따로 표시해요. 호환되지 않는 24 계열 노드가 먼저 실행돼도 호환되는 다른 설치본을 찾아요.
- 기본 빌드는 선택된 엔진을 갱신해요. 파이가 선택됐다면 `stock-engine`을 갱신하고, 기존 센파이 출력만 빌드한 뒤 성공으로 끝내지 않아요. 소스 지문으로 이전 실행본도 구별해요. `switch`는 선택만 하고, 명시적인 `update`가 재설치를 맡아요.
- 기본 `npm test`와 `npm run ci:local`에 파이 검사를 연결하고, 별도의 읽기 전용 자동 검사도 추가했어요. 기존 센파이 의존성 설치가 실패해도 이 검사에서는 독립된 파이 의존성 트리를 설치하고 검사해요.

## 사용하는 명령

파이 의존성을 처음 준비할 때는 저장소 루트에서 아래 명령을 실행해요.

```sh
npm --prefix harness/pi-runtime ci --workspaces=false --ignore-scripts
```

현재 선택된 엔진을 빌드하거나 소스와 일치하는지 검사해요. 오래된 실행본이면 검사 명령은 종료 코드 10을 반환해요.

```sh
npm run build
npm run build:check
```

파이 실행본만 명시적으로 갱신할 수도 있어요. 이 명령은 엔진 선택 표시나 인증·세션 파일을 바꾸지 않아요.

```sh
node harness/pi-runtime/scripts/switch-engine.mjs update
node harness/pi-runtime/scripts/switch-engine.mjs status
```

센파이 복귀용 실행본만 만들 때는 `npm run build:senpi`를 사용해요. 실행본 갱신 전에는 기존 세션을 종료해요. 실행 중인 프로세스에 교체한 파일이 즉시 적용된다는 뜻은 아니에요.

## 이번에 실행한 검사와 남은 검증

수정한 실제 모듈을 읽는 `test/migration-regressions.test.mjs`의 24개 검사를 리눅스·노드 22.16.0 환경에서 실행했고 모두 통과했어요. 이 검사는 파일시스템을 실제로 쓰며, 다운로드·조립과 파이 검증기·세션 인터페이스에는 시험용 구현을 넣어요. 원격 저장소 전체를 복제하거나 제품 의존성을 설치할 수 없는 작업 환경이라 파이 0.85.1 전체 실행 검사를 여기서 돌렸다고 주장하지 않아요.

새 `test/native-file-bridge.test.mjs`는 실제 파이 설치본과 입력 검증기, 세션 확장 처리, 커서 실행 연결을 함께 검사해요. 유료 모델 호출은 하지 않아요. 이 검사와 기존 전체 파이 검사는 새 자동 검사에서 실행하게 연결했지만, 이 문서를 작성할 때 원격 결과는 아직 확인하지 않았어요.

기존 기본 브랜치의 `bun install --frozen-lockfile` 실패는 남은 문제예요. 이 환경에서 번 1.4.0과 의존성 저장소를 이용해 잠금 파일을 재생성·검증하지 못했으므로 임의로 고치거나 고정 설치 검사를 우회하지 않았어요. 새 파이 검사의 통과와 기존 전체 자동 검사의 통과는 구분해야 해요.
