# 루바토에서 작업 의도를 함께 정하고 유지하는 방식

리드가 먼저 정보를 모아 실행 방향을 추천하고, 사람이 결정해야 하는 부분만 목적과
팀 구성에 묶어서 확인받는 방식이야. 사용자가 요구사항을 하나씩 설명하는 인터뷰를
기본 절차로 삼지 않아. 실제 운영 규칙은 `harness/skills/work-intent/SKILL.md`와
참조 지침이 맡고, 코덱스판은 `skill-bundle.json`으로 관리하는 사본이야.

## 2026년 자료에서 무엇을 가져왔는지

2026-09-11에 원문과 공개 날짜를 확인했어. 이번 변경의 근거는 2026년 자료만 사용했어.
아래 내용과 루바토에 맞춘 설계 선택은 구분해야 해. 어느 연구도 이 루바토 변경의
효과나 인텐트·팀 구성 통합 승인의 최적성을 직접 검증한 것은 아니야.

### 앤트로픽의 개발 생애주기 가이드 — 2026-08-21

[The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)

요청자의 말로 의도를 기록하고, 사람이 검토한 원본을 다음 단계가 직접 읽게 해.
사람이 명세를 처음부터 쓰는 대신 에이전트가 작성한 내용과 표시된 쟁점을 검토하는
흐름도 제안해. 단일 제품에는 저장소 안의 의도 보관 장소를 제안하고 있어.

다만 원문에는 의도를 구체화하는 질문과 구현 계획 인터뷰가 실제로 들어 있어.
따라서 이 글을 질문을 하지 말라는 근거로 쓰지는 않았어. 원본 연결과 사람의 검토는
채택하고, 먼저 조사한 뒤 필요한 판단만 묶는 대화 방식은 사용자의 요구에 맞췄어.
이건 공개된 적용 가이드이며 모든 내부 팀의 실제 운영을 입증하는 자료는 아니야.

### 앤트로픽의 장기 개발 실험 — 2026-03-24

[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)

짧은 요청을 계획 담당자가 구체적인 결과물로 확장하고, 구현과 검증을 분리한 사례야.
초기에 세부 구현을 틀리게 확정하면 오류가 다음 단계로 전파될 수 있어, 결과물을
명확히 하되 구현 방법은 작업 중 결정하게 했다는 설명이 있어.

리드가 방향을 먼저 제안하고 작업자에게 세부 방법의 재량을 남기는 데 참고했어.
실험의 적극적인 범위 확장 지침이나 추가 기능 제안까지 그대로 옮기지는 않았어.
여기서는 사용자에게 중요한 범위 변경을 먼저 보여주고 확인받아.

### 질문이 실제로 도움이 되는지 따지는 연구 — 2026-01-10

[Value of Information: A Framework for Human–Agent Communication](https://arxiv.org/html/2601.06407v1)

질문으로 얻는 판단상의 이득과 사용자에게 드는 수고를 함께 고려해 언제 물을지
결정하는 방법을 제안해. 모호함만 보고 질문하거나 정해진 횟수만 묻는 방식과 비교해.
다만 실험은 미리 정해진 질문·행동 후보와 단순화한 의사소통 비용을 사용해.
자유로운 개발 대화나 이 패키지의 질문 생성 방식까지 검증한 것은 아니야.

루바토에는 수치 계산기를 추가하지 않았어. 답에 따라 결과·제약·중요한 선택이 실제로
달라지는지 판단하고, 직접 알아낼 수 있는 정보는 먼저 조사하게 하는 원칙으로 옮겼어.

### 모호함과 잘못된 선택의 비용을 함께 본 연구 — 2026-05-24 개정

[Act or Clarify? Modeling Sensitivity to Uncertainty and Cost in Communication](https://arxiv.org/html/2602.02843v3)

최초 공개는 2026-02-02이고, 확인한 최신 개정은 2026-05-24야. 논문 페이지에는
2026년 인지과학 학술대회 채택이 표시되어 있어. 인간의 질문 행동을 실험하고,
불확실성과 잘못 행동했을 때의 손실을 함께 고려하는 설명을 제안해.

무조건 질문을 줄이자는 근거가 아니라, 중요한 결과가 달라지는 선택은 사람에게
남겨야 한다는 보완 근거로 썼어. 코딩 에이전트나 통합 승인 절차의 직접 실험은 아니야.

### 저장소에서 숨은 요구를 복원하는 평가 — 2026-08-10

[A Unified Issue Resolution Benchmark for Requirement Clarification, Planning, and Code Generation for Coding Agents](https://arxiv.org/abs/2608.09072)

공개 초록은 최종 코드의 통과 여부뿐 아니라 요구사항 파악과 저장소에 근거한 계획을
함께 평가한다고 설명해. 명시되지 않은 요구를 복원하는 부분을 주요 어려움으로 보고해.
코드만 바로 수정하기보다 기존 동작과 계약을 먼저 확인하는 방향에 참고했어.

이 자료는 초록과 제출 이력만 확인했어. 전체 실험을 감사하거나 인터뷰보다 저장소
조사가 우수하다는 인과 효과를 확인한 것으로 쓰지 않았어. 이번 설계는 앞의 공식 사례와
의사소통 연구, 사용자 요구를 함께 고려한 선택이야.

## 이번에 정한 실행 흐름

현재 요청과 이미 정해진 사항을 먼저 읽어. 저장소·문서·연결된 자료로 알 수 있는 것은
직접 확인하고, 외부 사실이 필요할 때만 최신 공식 자료를 조사해. 모든 도구를 순서대로
쓰는 절차는 아니야. 방향·분업·완료 판단에 충분한 정보가 모이면 조사를 멈춰.

찾아서 알 수 있는 사실은 리드나 조사자가 해결해. 승인된 범위 안의 구현 방법도
작업자가 결정해. 사용자의 목표·선호·호환성·비용처럼 중요한 결과를 바꾸는 선택은
추천안과 그 차이를 함께 보여줘. 접근할 수 없는 사실은 없다고 단정하지 않고 남겨.
그 사실이 제안 자체를 막을 때만 필요한 정보나 접근 하나를 먼저 물어봐.

팀이 필요한 작업에서는 목적·추천 방향·유지할 것·완료 판단과 최소 팀 구성을 한 번에
제안하고, 둘 다 확인받은 뒤 팀을 만들어. 파이와 코덱스 모두 같은 원칙이야.
사용자가 인텐트만 승인했다거나 팀만 좋다고 한 답은 나머지 승인으로 넓히지 않아.
분명한 수정을 붙여 승인하면 그 내용을 반영하고, 새 중요한 미결정 사항이 없다면
똑같은 확인을 반복해서 받지 않아.

조사자는 승인 전 초안을 읽고 제한된 정보 수집을 할 수 있어. 구현 담당자를 먼저
띄워놓고 조사라고 부르지는 않아. 기존 모델·비용·프레이밍·전달 권한은 여전히 지켜.
승인 뒤 같은 담당자가 수정·검증을 이어가거나 동일하게 복구할 때는 다시 묻지 않아.
중요한 목적이나 팀·비용이 달라지면 바뀐 부분만 함께 확인해.

## 문서와 승인 기록을 어디에 두는지

의도는 기존 원본을 재사용하거나 `intent/<식별자>/intent.md`에 보관해. 같은 목적은
세션이나 팀이 바뀌어도 같은 기록을 써. 인텐트 본문은 사용자의 언어로 적고,
프로그램이 읽는 고정 제목만 기존 형식을 유지해. 사용자에게 승인받는 메시지는
그 제목이나 식별자·경로를 그대로 쏟아내지 않고 결과가 어떻게 달라지는지 설명해.

임무 문서는 제안 메시지, 그때 보여준 인텐트 개정, 실제 승인 답변과 정확한 팀 구성을
참조해. 새로운 승인 장부나 요구사항 사본은 만들지 않아. 관리 도구로 활성화하면
파일 지문이 달라지므로 새로 반환된 참조를 작업서와 작업판에 전달해.

관리 도구는 상태·지문·개정 충돌을 검사하지만 승인 문장의 진위를 판정하지 않아.
통합 승인과 질문 절제는 지침을 따르는 모델의 동작이고, 실행 도구를 가로채 강제하는
새 장치는 추가하지 않았어. 일반 소규모 작업에는 팀이나 문서·승인 절차를 만들지 않아.

## 변경 경로와 확인 방법

리드 시스템 지침, 두 태스크포스 판본, 운영 규칙, 파이의 모델 배치 예시와 팀 생성
도구 설명을 같은 승인 원칙으로 맞췄어. 위임·수신 지침에는 초안 조사 예외와 현장에서
사실을 확인하는 책임을 연결했고, 코덱스 생성 역할에도 수신 지침을 다시 반영해.
이전의 사전 보고 방식을 요구하던 회귀 시나리오도 사용자 요구에 맞게 바꿨어.

```sh
node --test harness/rubato-pi/test/unit/work-intent.test.mjs rubato-codex/test/work-intent.test.mjs
node rubato-codex/scripts/build-skills.mjs --check
node rubato-codex/scripts/build-roles.mjs --check
```

저장 도구 시험, 지침 연결과 생성물 검사, 실제 모델 동작 시험은 구분해.
`harness/prompts/evals/rail-choice.yaml`에는 조사·제안·사용자 답·실행을 이어서 확인하는
사례를 넣었어. 실제 모델을 실행하지 않은 사례를 구조 검사 통과로 대신 처리하지 않아.
사용자에게 쉬운 말로 설명하는지, 필요한 질문만 묻는지도 실제 대화 기록에서 봐야 해.
