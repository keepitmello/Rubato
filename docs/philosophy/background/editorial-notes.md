# 이번 문안을 정리하며 내린 편집 결정

이 글은 철학 본문을 고치거나 현재 스킬과 비교할 사람이 읽는 기록이다. 사용자와 합의한 방향을 어떤 구조로 풀었는지, 과거 자료에서 무엇을 이어받고 무엇을 구현의 선택으로 남겼는지 설명한다.

## 공통 철학 하나와 주제별 글로 나눈 이유

공통 글은 왜 루바토를 만드는지와 무엇을 우선하는지 맡는다. 사고 방식, 팀 운영, 가벼운 하네스는 그 목적을 각각 다른 문제에 적용한다. 대화와 문헌, 현재 지침의 연결은 배경 자료에서 다룬다.

| 파일 | 이 파일에서 정하는 것 |
|---|---|
| `../README.md` | 목적, 우선순위, 문서들 사이의 관계 |
| `../thinking.md` | 발산과 수렴, 목적 합의, 관점 이동, 모델과 세션 배치의 사고 기준 |
| `../taskforce.md` | 리드·오너·검증자의 책임, 직접 협업, 통합, 맥락과 결과의 연결 |
| `../lightweight-harness.md` | 상시 맥락, 지침과 기능의 분담, 대기와 재사용, 유지보수와 개선 |

각 본문은 따로 읽어도 맥락을 이해할 수 있도록 필요한 배경을 짧게 포함했다. 공통 우선순위를 새로 정의하거나 같은 운영 절차를 여러 파일에 복제하지는 않았다.

## 이번 대화에서 확정된 내용을 앞에 놓았다

### 우선순위를 다시 정리했다

초기 제안에 있던 “완성도와 속도를 높이는 팀”이라는 표현만으로는 사용자의 우선순위를 충분히 드러낼 수 없었다. 현재 문안에서는 토큰과 시간을 우선 아끼고, 합의한 목적에 맞는 품질을 함께 확보한다고 썼다.

이는 품질을 포기한다는 뜻도, 성능을 최대한 높이는 것이 최상위 목표라는 뜻도 아니다. 필요한 품질을 실제 목적에 연결하고, 더 많은 비용과 시간을 쓰는 선택은 그 이득을 보고 판단한다.

### 리드를 사용자와 대화하는 역할로 중심에 놓았다

사용자의 최신 설명은 리드가 사용자 대신 여러 작업을 이해하고 정리하고 조율하는 수고를 맡는다는 것이다. 그래서 팀 구조보다 이 목적을 먼저 설명했다.

리드의 구현 역할을 따로 열어두지 않았다. 팀이 맡은 결과의 실제 구현과 통합 작업은 오너가 이어가고, 리드는 사용자와 목적을 정하고 팀 전체의 선택과 완료를 판단한다. 목적과 임무를 기록하고 사용자에게 설명하는 문서는 리드가 맡는다.

일반적인 작은 일을 단일 작업 세션으로 처리하는 선택도 유지했다. 이를 팀을 운영 중인 리드가 오너의 구현을 대신 떠안는 예외로 해석하지 않도록 구분했다.

### 검증자를 작업 과정에 연결했다

새 문안은 검증자를 마지막 판정 시점에만 등장시키지 않는다. 중요한 가정과 중간 결과를 확인할 때부터 오너와 직접 협업하도록 설명한다.

협업하면서도 각자의 판단 근거를 유지한다. 제품 변경과 수정 책임은 오너에게, 실제 결과와 확인 기준을 독립적으로 살피는 책임은 검증자에게 둔다. 검증자가 자체 재현이나 확인 자료를 준비할 수 있는 재량도 살렸다.

참여를 일찍 연결하는 것과 호출을 자주 하는 것은 구분했다. 이로써 동료 협업과 자원 절약이 함께 유지되게 했다.

## 겉으로 충돌할 수 있는 생각을 이렇게 연결했다

### 사고는 나누고, 발견은 서로 전달한다

발산과 수렴을 별도 세션으로 나눈다는 원칙을 채택했다. 동시에 오너가 자기 범위에서 가설과 구현 방법을 탐색할 재량도 보존했다. 역할은 사고 능력을 제한하는 구분보다 지속해서 맡는 문제의 범위를 정하는 구분으로 설명했다.

현장의 발견이 목적을 바꾸는 경우에는 리드와 사용자에게 연결한다. 목적의 변경이 필요한 사실을 통째로 가리는 구조도, 모든 로컬 가설 변경을 리드에게 넘기는 구조도 본문에 넣지 않았다.

### 동료는 동등하고, 결정의 범위는 다르다

리드·오너·검증자의 동등함을 각자가 독립적으로 판단하고 맡은 책임을 가진다는 뜻으로 풀었다. 전체 목적과 공동의 선택, 로컬 구현, 독립 판정은 역할에 따라 구분한다.

부모·자식 프로세스나 세션 깊이라는 구현 표현은 본문에서 최소화했다. 필요한 구현 해석은 아래 대응 표에서 확인할 수 있다.

### 맥락은 가볍게 유지하고, 판단 근거는 연결한다

초안의 “상태 핑과 파일 경로만”은 리드에게 긴 작업 서사가 쌓이는 것을 줄이려는 방향으로 읽었다. 현재 문안에서는 판단을 바꾸는 핵심과 영향, 근거를 찾을 경로를 함께 전달한다고 정리했다.

정보량을 줄이면서도 목적과 결정 이유, 정정된 사실은 유지한다. 필요한 원자료를 직접 확인할 길을 남겨 짧은 요약이 새로운 오해의 원인이 되는 문제도 줄이려 했다.

### 세션은 재사용하고, 독립된 시각은 필요에 따라 확보한다

이미 이해한 담당자를 이어 쓰는 원칙을 우선했다. 새 문제를 맡기거나 독립된 판단을 새로 얻을 필요가 있을 때는 새 세션을 선택한다.

모든 역할과 단계에서 세션을 새로 만들거나, 반대로 어떤 상황에서도 같은 세션을 유지하는 의무는 넣지 않았다. 계속 쓰는 이득과 새로 보는 이득을 현재 작업에 맞춰 판단하게 했다.

### 적은 규칙과 필요한 실행 기능을 함께 둔다

긍정적인 목적과 역할, 재량, 정보 접근을 먼저 설명했다. 정해진 권한과 자원, 상태 보관처럼 하네스가 명확히 처리할 수 있는 일은 기능으로 뒷받침한다.

리드가 일을 대신하지 못하게 막는 것만으로 협업을 구현했다고 보지 않는다. 오너와 검증자가 직접 연락하고, 결과를 찾고, 후속 작업을 이어갈 수 있는 경로가 함께 필요하다. 이는 현재 역할을 구현할 때 검토할 설계 조건이지, 그 기능이 이미 검증됐다는 보고가 아니다.

## 초안에서 철학과 구현을 나눈 부분

| 초안 또는 과거 자료의 표현 | 철학에 남긴 뜻 | 구체적인 선택을 두는 곳 |
|---|---|---|
| “인지상 깊이 0” | 리드·오너·검증자가 독립된 판단과 책임을 가진 동료라는 관계 | 역할 지침과 실행 환경별 세션 설명 |
| `fork=none` | 새 세션에 필요한 목적과 자료를 정제해 전달한다는 원칙 | 실제 생성 도구와 환경별 지침 |
| 리드는 가장 비싼 최상위 모델 | 사용자와 큰 그림을 다룰 판단력을 확보한다는 목적 | 사용자 선택과 현재 모델 배치 지침 |
| 깨어나는 순간을 두 종류로 고정 | 실행과 대기를 분리하고 중요한 판단에 집중한다는 원칙 | 알림·재개·사용자 응답의 실제 구현 |
| 파이는 팀, 코덱스는 단일 작업 | 실행 환경이 바뀌어도 같은 팀의 목적을 이어간다는 원칙 | 환경별 기능과 실제 제약을 기록한 운영 문서 |
| 다른 모델 계열의 검증자 | 다른 계열을 우선 고려해 서로 다른 시각을 확보하고 직접 확인한 근거로 판단한다는 방향 | 특정 모델의 고정 조합과 작업별 검증 구성 |
| 단계마다 새 검토자 | 새 시각이 유용한 순간에 독립 확인을 확보한다는 목적 | 비용과 필요에 따라 정하는 검토 시점 |
| 토큰 비용은 맥락 길이에 비례 | 읽는 맥락과 활동 횟수, 재조사 비용을 함께 아낀다는 방향 | 실제 사용량과 과금·쿼터의 실측 자료 |
| 삭제·문장·양식·절차·구조의 사다리 | 먼저 겹침과 충돌을 정리하고 문제에 맞는 작은 변경을 선택한다는 방향 | 스킬과 코드 개정의 구체적인 작업 순서 |

위 대응은 오래 쓸 목적을 남기기 위한 편집이다. 개별 구현이 잘못됐다고 판정하거나 실제 기능을 변경한 것은 아니다.

## 현재 지침과 앞으로 대조할 지점

이번 작업은 문서 읽기와 철학 작성이다. 실제 팀을 실행해 행동을 측정하거나 코드를 수정하지 않았다. 다음 항목은 철학과 구현을 연결할 때 참고할 지점이며, 동작상 결함이 확인되었다는 목록이 아니다.

**검증자의 합류 시점과 첫 임무.** 현재 검증자 지침에는 오너에게 직접 실패를 반환하는 경로가 이미 있다. 사용자가 경험한 사후 리뷰 흐름의 원인은 그 문구만으로 확정할 수 없다. 실제로 언제 합류했고 어떤 일을 맡았는지, 중간 결과를 받을 경로가 있었는지를 함께 봐야 한다.

**통합 작업의 담당자.** 현재 문서의 “리드가 통합한다”는 표현은 통합을 판단하는 일과 실제 변경을 합쳐 고치는 일로 읽힐 수 있다. 새 철학에서는 구현과 통합 작업을 오너에게, 전체 결과와 완료 판단을 리드에게 두었다.

**검증자의 협업과 새 검토 세션.** 현재 운영 모델에는 검증자가 구현 논의에 깊이 참여한 장기 작업에서 새로운 검토자를 쓰라는 설명이 있다. 새 철학은 작업 중의 협업을 살리되 별도의 확인 근거를 유지한다. 새로운 세션을 쓰는 시점은 이 목적과 실제 비용을 함께 고려해 구체화할 부분이다.

**직접 소통과 상태 접근.** 철학이 원하는 것은 오너끼리, 오너와 검증자가 바로 협업하는 관계다. 실제 하네스의 통신과 상태 노출이 이 관계를 쉽게 만드는지는 실행 기록으로 확인할 부분이다.

**리드의 대기와 사용자 응답.** 리드가 실행 기록을 계속 읽으며 기다리는 비용을 줄이면서도 사용자와의 대화는 이어져야 한다. 실제 환경에서 세션을 보존하고 필요한 사건에 다시 참여하는 방식은 별도 구현 과제다.

## 문서의 표현과 근거를 정리한 기준

철학 본문은 추구하는 상태와 행동을 긍정형으로 적었다. 운영 명령의 나열보다 각 역할을 그렇게 둔 이유가 이어지도록 구성했다. 기술적인 식별자와 세부 명령은 필요한 배경 자료에 남겼다.

현재 사용자가 승인한 가치와 이번에 읽은 과거 문서의 제안을 구분했다. 대화에서 만들어진 문서를 원대화처럼 쓰지 않았고, 확인하지 못한 엔비디아 논문의 내용을 일반 연구로 채우지 않았다. 당시 모델 성능과 도구의 장단점도 현재 사실로 다시 주장하지 않았다.

주제별 글은 저장소에서 사용할 문안으로 작성했지만, 이번 작성만으로 기존 스킬과 코드가 새 철학을 구현했다고 말하지 않는다. 설계를 고칠 때 이 문안과 실제 운영을 대조할 수 있도록 구성했다.
