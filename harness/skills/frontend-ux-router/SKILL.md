# Make a result the intended user can understand and use

A screen is not an inventory of the data available to implement it. Arrange the evidence, actions and feedback around what the person is doing. For passive viewing, orientation or exploration, do not invent a primary action merely to satisfy a design formula.

For creation or redesign read `references/frontend-creation.md`; reuse it when already in context. Read a specialist reference only for a material decision it can improve. Keep the current task owner. Product constraints, accessibility, explicit preview/review requirements, write authority and release conditions continue to bind; a planning request is not permission to edit the product.

## Composition and repair

Start with the actual path and content. Familiar words and native evidence should let the first view make sense without the builder's coaching. A real picture or control state can explain what a count cannot. Keep internal identifiers and invented encodings out of visible copy unless they are legitimate content for that audience.

When the result is crowded, remove duplicate explanation or establish hierarchy among necessary parts. Preserve the job of a removed element; a self-chosen layout budget is not a reason to delete approved content. A small capture may call for a crop, a closer view or a different composition before asking the user to make a new asset. Recreate a screen only as an honestly identified mockup, not as proof of an observed live state.

Reference material supplies relationships, not a mandatory bundle of parts. Compare coherent experiences when the question is about the whole result, and isolate a variable when its effect is the question. There is no required candidate count, one-button quota, one-device rule or automatic mixture of the user's favorite parts. Express mood through a coherent visual and interaction system, rather than a label or isolated effect.

If words remain difficult after being simplified, inspect the missing context or the choice of scene. More labels cannot rescue a misleading task model. A local defect calls for a local repair; repeated repairs that undermine each other can justify redesign inside the approved dimensions. Preserve explicit freezes, not every value of a baseline kept only for comparison.

## Evidence and completion

Observe the changed property and coupled behavior in the rendered path. New interaction needs relevant action, feedback, recovery and resume on its intended platforms; a build or static frame cannot establish full-speed control feel. Reuse evidence only while its target and dependencies remain valid. Named product, accessibility and release checks still apply. Protect explicit frozen items at the strongest meaningful level available, with an assertion, contract check, snapshot or named definition, and keep their source and date; a prose promise or an old value left in a comment is not protection, and a snapshot proves only the property it measures. Report a protection gap honestly.

Use a separate observer when first-reader comprehension or an independent challenge can change acceptance, and when review is explicitly required. A comprehension-only observer starts with what a real user would see, before the builder's explanation; a goal reviewer also receives the actual goal and binding constraints. Neither certifies the user's taste, and every visual edit does not require another reviewer.

Within the assignment, return a judgment-ready artifact and repair omissions you can inspect yourself. An assigned preview is a valid completion; a first screenshot missing promised behavior is not. Honor an explicit checkpoint or stop, report genuine blockers, and show a useful preview when taste is the remaining question rather than polishing unseen. Give a recommendation instead of a list of defects for the user to diagnose.

## Apply the right reference without restarting the work

Inspect current artifacts before additional research. Use state patterns when asynchronous behavior, permissions, loading or recovery affects the path; use the full heuristic guide for an audit, not as a mandatory extra pass on every edit. Read the failure study when its review/labeling problem matches the task or helps distinguish repeated confusion.

`frontend-creation.md` is the creation guide if an older specialist recipe conflicts with it. A specialist's old checklist cannot create a universal quota or approval gate. Existing product design language is a starting point; an authorized redesign may reconsider it. Use images for appearance, motion for timing and operation for control feel, according to the decision rather than a required medium.

The worker returns the artifact, observed behavior, meaningful gaps and the required intent/Frozen items/Open variables references. The dispatcher handles in-scope correction before forwarding work. Keep detailed commands at existing artifact locations; tell the user the result, recommendation and any real choice in ordinary language. Unknown is not failed, and unperformed is not passed. A narrow audit is not unsolicited permission to redesign.
