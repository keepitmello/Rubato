## framing이 뭔가

만들기 전에 "누가, 어떤 순간에, 지금은 뭘로 때우고 있고, 이게 왜 나으며, 그래서 뭐가 달라지는가"를 확정하고 잠그는 착수 전 점검표. 하는 일은 세 가지:

1. **요구사항 구체화 압박** — "일반 사용자", "더 편리하게" 같은 걸 결격 사유로 걸러냄
2. **확정·동결** — 6가지(사용자, 트리거, 현재 대안, 약속한 아웃컴, 비교 가치, 도입 경로)를 못 바꾸는 약속으로 잠그고, UI·기술스택은 자유로 둠. 바꾸려면 동결 해제 절차를 밟아야 해서 조용한 표류가 불가능해짐
3. **검증 순서 강제** — 제일 위험한 가정을 제일 싼 실험으로 먼저, 성공 기준은 결과 보기 전에 고정

판의 무게 3단계: **연습**(버려도 되는 실험, 칸 5개만·몇십 분) / **무대**(해커톤 등 외부 평가, 전체 + 독립 레드팀) / **실전**(진짜 고객·돈, 추가 검토).

만들어진 계기: KB 해커톤에서 "이 제품의 가치가 뭔지"가 구현 중에 흐려져서 마감 2시간 반 전에야 가치 정리가 나왔던 것. 이 스킬이 있으면 그 정리가 코딩 시작 조건이라 새벽에 이미 나와 있어야 한다.

## reframing이 뭔가

한 프레임에 매몰돼 진전이 없을 때 프레임 밖 시각을 강제로 확보하는 발산 장치. KB 때 아버지 역할의 구조화다:

- "치매 진단하자"에 매몰 → 아버지의 "진단하고, so what?" → 사슬이 진단에서 끊긴 걸 발견 → 리서치해 보니 KB에 진단 인프라도 시니어 보험도 이미 있는데 **다리만 없더라** → "다리 역할"로 프레임 확정. (원문: 로컬에 있다면 `~/.claude/roo-channel/notes/reframing-원안.md`)

프로세스: 매몰 선언 → **so-what 체인**(사슬 끊긴 지점 찾기, 독립 시각 여럿을 병렬 블라인드로 — 매몰 탈출엔 지능을 아끼지 않는다) → **브릿지 리서치**(그 조각이 이미 세상에 있나) → 대안 프레임 후보 1~3개.

레드팀과 다르다: 레드팀은 "이 프레임이 왜 틀렸나"(부수기), reframing은 "완성되려면 뭐가 빠졌고 그 조각이 어디 있나"(잇기).

## 순서가 헷갈릴 때

reframing은 framing의 다음 **단계**가 아니라 **비상구**다. 계단은 framing 하나로 쭉 올라가고, reframing은 막혔을 때만 여는 문이다. "re"가 붙은 이유는 프레임이 **이미 있어야** 다시 잡을 수 있어서고("프레임 한 문장을 못 적으면 framing부터"), 반드시 거친다는 뜻이 아니다.

```
framing 탐색 (잠정 프레임 + 후보 3종)
  ├─ 잘 수렴함 → 동결 → 구현 → 끝. reframing 안 씀 (정상)
  └─ 막힘 (후보 전부 비슷, 가치 설명이 꼬임)
        → reframing (탈출, 새 후보)
        → framing 복귀 → 동결
```

reframing이 자주 불려나오면 프레임을 너무 얕게 잡고 시작한다는 신호다.

## 실제 사용 장면 세 개

1. **새 아이디어**: `/framing 아이디어 한 줄` → 티키타카 → 동결 → 구현. 대부분 이걸로 끝
2. **framing 도중 답답**: 메인 세션이 매몰 신호(후보 전부 유사, 같은 접근 반복 실패)를 감지하면 먼저 reframing을 제안한다. "ㄱㄱ"만 하면 됨
3. **점검표 없이 만들던 게 현타**: `/reframing` 단독. 나온 후보가 좋으면 그때 framing으로 정식 검증, 아니면 대화로 소화하고 끝

둘은 완전 독립이라 하나만 써도 되고, 조합하면 위 루프가 된다.

## 그밖에

- 사람이 결정하는 것: 사실, 가치판단, 최종 프레임 선택, 승인. 모델은 후보 생성·모순 지적·검사만 (린터이지 결정권자가 아니다)
- 시작할 때 사용자의 날것 아이디어를 원문 그대로 박제한다 — 나중에 스킬이 실제로 값을 했는지 재는 대조군
- 무대 이상은 후보 산출도 교차 모델 병렬로 — 같은 모델이 낸 "다른 안"은 같은 사고의 변주인 경우가 많아서
