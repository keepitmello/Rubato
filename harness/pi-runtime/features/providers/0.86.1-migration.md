## Open blockers (not caused by this migration)

Both reproduce on the live 0.85.1 stage, so neither is a 0.86 artifact.

1. **`providers.test.mjs` "registers all seven" fails with 8 ids.** Stock 0.86.1
   added a `meta` (Meta Muse) builtin provider. `createProvidersExtension`
   narrows the registered set by unregistering
   `foreignProviderIds(builtinProviderIds())`, and `BUILTIN_PROVIDER_IDS` in
   `harness/rubato-pi/src/provider-ids.mjs` is a frozen snapshot from the
   previous pin, so `meta` is never swept and leaks into Rubato's provider
   surface. The designated drift detector
   `harness/rubato-pi/test/unit/provider-ids.test.mjs` cannot see it: it
   resolves the catalog through `senpiNested`, i.e. the retired senpi fork, not
   the stock engine. Exact drift measured against stock 0.86.1: `meta` is the
   only missing id (it belongs between `kimi-coding` and `minimax`). The fix
   belongs in `harness/rubato-pi/src/` — outside this feature's write scope.

2. **`auth-pool.test.mjs` "keeps a session on the first account after a
   pre-output 429" fails at the third call.** `87a70f86c` added
   `requiredSlotName: requiredAccountSlotName(model, slots)` to
   `streamWithCredentialPool`, which pins a *base* model to the non-sub slot.
   With `[default, login-2]` the base model is pinned to `default`; after two
   429s `default` is in cooldown, so the new session cannot hop and dies with
   `Account 'default' is unavailable`. That commit's own
   `auth-pool-sticky.test.mjs` asserts the pin for `-sub` models and the
   setup-token lane, so the pin is intended for those; the
   base-model-with-a-sibling-login case is unspecified and is what kills
   cross-session failover. Needs a product call: pin only for
   `-sub`/setup-token, or accept that a base model cannot fail over. The
   assertion was left untouched rather than rewritten, because it is the only
   guard on cross-session failover.
## Addendum 2026-09-21 — blocker outcomes

**Blocker 1 closed (by the lead).** `harness/rubato-pi/src/provider-ids.mjs`
gained `"meta"` between `kimi-coding` and `minimax`, and its comment no longer
attributes the snapshot to Senpi 2026.9.4-3. The detector
`harness/rubato-pi/test/unit/provider-ids.test.mjs` now reads the catalog from
the stock engine instead of `senpiNested`, and its assertion became one-way —
"no stock builtin is missing from the frozen list" — because a missing builtin
is what leaks into Rubato's surface while extra frozen entries are harmless.
Independently re-verified here: `providers.test.mjs` 13/13,
`provider-ids.test.mjs` 3/3.

**Blocker 2 open — escalated to the user, assertion held unmodified.** The
write-up above stands as written. The lead's stated recommendation is to pin
only when the model names a subscription identity (`-sub`) or a setup-token lane
exists, because `requiredAccountSlotName` falling through to
`slots.find((s) => s.name !== subName)` picks an arbitrary sibling and turns one
account's cooldown into a session-wide outage. No decision yet.

Feature test state with blocker 1 closed: 76 tests, 75 pass, 1 fail (blocker 2).

**Evidence boundary (raised by the verifier, accepted).** "Composition staging
ready" proves exactly three things: `preimageSha256` matches the installed
0.86.1, the selected files compose in order, and the receipt reports
`stockVersion: 0.86.1` / `state: ready`. It does **not** prove the candidate
entry runs — `build-candidate.mjs` and `validateCandidateStage` never import it,
so a missing payload module survives staging. That gap is real and was hit:
`features/rubato-components/candidate-main.mjs` imported `./pi-version.mjs`
before the lead moved the single source to
`features/rubato-components/pi-version.mjs` and made the root module re-export
it, which killed the staged entry with `ERR_MODULE_NOT_FOUND` and also killed
`model-picker.test.mjs` at import time. Do not read staging green as execution
evidence for this batch.
