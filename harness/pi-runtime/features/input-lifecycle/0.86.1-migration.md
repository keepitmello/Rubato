# 0.86.1 patch judgments

Judged against the installed `@earendil-works/pi-coding-agent` 0.86.1 (the tree
`stage-runtime.mjs` verifies against; byte-identical to the 0.86.1 tarball).
Old-side oracle: the pristine 0.85.1 tarball. Every broken patch below was read
next to what changed around its anchor, not re-recorded on the hash alone.

`delete` count: 0. No 0.86 feature absorbs these intents — a postimage search
finds nothing in 0.86.1 for any patch in the whole 146, so absence proves
nothing; each keep/re-cut is argued from the 0.86.1 source instead.

6 patches, all 6 were broken (2 anchor-dead).

| patch | judgment | reason |
|---|---|---|
| `dist/core/agent-session.js` | **re-cut** | `prompt-input-event`, `prompt-handled` and `prompt-started` anchors died. 0.86 moved the `input` emission into `_runInputHandlers` — shared by `prompt()` and the new `_queueUserInput()` for `steer()`/`followUp()` — and removed the `agent.state.systemPrompt` assignment. Re-cut: `begin()` lives in `_runInputHandlers` so both callers get an id, the "handled" disposition is emitted where the handling decision is made, `_queueUserInput` also emits "queued", and "started" moved to the point where the prompt definitely runs. Giving `steer()`/`followUp()` ids is the same intent applied to the new seam: without one they would emit an `input` event with no id and fall back to stock string-identity queue removal, which is the defect this feature exists to remove. |
| `dist/core/extensions/types.d.ts` | **re-cut** | `types-api-overload` anchor died: `on` now returns `() => void`. |
| `dist/core/extensions/runner.js` | keep | `emitInput`'s signature and the input-event literal are unchanged, so our added `inputId` still lands in the same place. |
| `dist/core/extensions/runner.d.ts` | keep | The `emitInput` declaration is unchanged. |
| `dist/core/extensions/index.d.ts` | keep | Our export anchor is intact. |
| `dist/index.d.ts` | keep | Same. |

The `_queueSteer(text, images, inputId)` / `_queueFollowUp(text, images, inputId)`
shapes and the `prompt` bindMessage block are unchanged, so `request-run`'s
consumer anchors still bind (verified by composing both in one stage).
