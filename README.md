# Rubato

**매일 쓰는 멀티모델 에이전트 하네스. 사람이 병목이 되지 않게.**

에이전트를 여러 개 굴리면 정작 당신이 관리자가 된다. 수많은 텍스트를 읽고, 판단하고,
방향을 잡고, 틀리면 되돌리고, 다시 시킨다. 그 인지부하가 병목이다.

Rubato는 그 자리를 리드에게 넘긴다. 당신은 무엇을 얻고 싶은지, 어떤 선택이 중요한지만
이야기한다. 리드가 목적을 구체화하고, 필요할 때만 태스크포스를 만들고, 팀이 알아낸 것을
당신이 판단할 수 있는 말로 돌려준다.

동시에 하네스는 **캐시를 지키는 데 집착한다.** 접두사 히트율 98–99%를 목표로 잡고,
컨텍스트에 노이즈가 섞이는 것을 막는다. 그래야 빠르고 싸고, 오래 써도 똑똑하다.

이름은 *tempo rubato* — "훔친 시간"에서 왔다. 박자를 강제하는 대신 모델이 문제에 맞게
생각할 시간을 조절한다.

## 왜 만들었나 — 사람이 병목이 된다

에이전트를 여러 개 쓰면 사용자가 맡는 일이 하나 늘어난다. 일을 나누고, 각 세션이 뭘
알고 있는지 기억하고, 결과를 읽어 맞춰보고, 다음에 뭘 시킬지 정하는 일이다. 모델이
똑똑해질수록 당신은 관리자 자리로 밀려나고, 읽을 텍스트와 판단할 거리만 늘어난다.

그래서 그 자리를 맡을 **리드**를 두고, 필요할 때 **태스크포스**를 꾸린다. 사용자는
리드와 방향을 함께 잡고, 리드는 실행을 맡은 동료들이 각자 일을 진전시키는 동안 목적과
열어둔 선택을 쥐고 있다. 작업자마다 브리프를 쓰고 보고를 읽어 다음을 정하는 일은
사용자에게서 리드로 넘어간다.

당신에게 돌아오는 것은 진행 상황이 아니라 **판단이 필요한 것**이다.

## 캐시를 지키는 하네스

Rubato가 빠르고 싼 이유의 대부분이 여기에 있다.

모델 API의 입력 비용은 대개 **접두사 캐시**가 결정한다. 요청 앞부분이 직전 요청과
바이트 단위로 같으면 그 부분은 캐시 읽기로 값을 매기지 않는다. 반대로 앞부분이 한
글자라도 바뀌면 그 뒤가 통째로 다시 계산된다. 그래서 접두사를 건드리는 모든 것이
설계 대상이 된다.

```
직전 요청  [ 시스템 지침 | 도구 정의 | 대화 1 … 대화 N ]
다음 요청  [ 시스템 지침 | 도구 정의 | 대화 1 … 대화 N | 새 턴 ]   → 앞부분 그대로, 캐시 적중
다른 요청  [ 시스템 지침 | 도구 정의 | 요약 | 새 턴 ]              → 앞부분이 바뀜, 전부 다시 계산
```

- **히트율이 눈에 보인다.** 상태줄에 `(CH: 98%)`로 뜨고, 끝난 실행은 지출과 함께 그
  실행 전체의 히트율을 남긴다. 보이지 않으면 지킬 수 없다.
- **창을 넘길 때 요약으로 접두사를 갈아엎지 않는다.** 대신 모델이 작업 노트를 쓰고 새
  창으로 넘어간다. 새 창에는 창 식별자와 노트 목록만 들어가고, 노트 본문과 과거 원문은
  모델이 필요할 때 도구로 다시 읽는다. 자동 요약을 대신 써 넣지 않는다. 지금은 시작
  모델이 아스트라일 때 이 방식이 기본이고, 다른 모델은 기존 요약이 기본이다.
- **이미 보낸 것을 나중에 고치지 않는다.** 창마다 한 번 기록한 안내는 토큰 수가 달라져도
  바꾸지 않는다. 위치를 복원할 수 없으면 **캐시를 위해 임의로 옮기지 않고 중단한다.**
- **도구 출력이 컨텍스트를 밀어내지 못하게 한다.** 16KB를 넘는 도구 결과는 8KB만 보여
  주고 나머지는 파일 경로로 남긴다. 원문은 필요할 때 범위를 지정해 읽는다. 요약해서
  넘기지 않는다 — 코드를 요약하거나 성공을 추정하지 않는다는 규칙이 있다.

히트율은 프로바이더에 따라 갈린다. Anthropic 직결과 OpenAI Codex 경로에서 접두 재사용을
확인했고, Cursor 경로에서는 같은 53KB fixture로 접두 히트 98.7–99.1%가 나온다. 아직
조사 중인 경로도 있다.

## 컨텍스트가 곧 성능이다

요즘 프론티어 모델은 빡빡한 규칙을 제약으로 받는다. 그리고 컨텍스트에 불필요한 것이
섞이면 그대로 성능 저하다. 그래서 상시로 읽는 것을 줄이고, 목표를 분명히 하고, 나머지는
필요한 순간에 읽는다.

- **상시 역할 프롬프트가 약 6KB다.** 목적과 책임, 선택의 경계만 담는다. 어떤 문제를
  맡고 어디까지 스스로 정할 수 있는지가 적혀 있고, 방법은 적혀 있지 않다.
- **스킬은 필요한 순간에 읽는다.** 목록에는 이름과 설명만 뜨고, 본문은 그 판단이 필요할
  때 들어온다. 상시로 읽는 부담과 발견하기 쉬운 정도를 함께 맞춘다.
- **오래 쓸 지식은 대화 밖에 둔다.** 세션에 쌓아 두는 대신 검색 가능한 기억(`msearch`)에
  넣고 필요할 때 꺼낸다. 대화에는 다음 행동을 바꾸는 근거만 남는다.
- **판단을 구조로 대체하지 않는다.** 절차와 gate는 "판단하라고 명시했는데도 안 한" 실패가
  관찰된 뒤에만 넣는다. 기본값과 누락에 의미를 싣지 않는다.

## 태스크포스는 서브에이전트와 다르다

일반적인 서브에이전트는 부모가 띄우고, 결과 요약이 부모의 컨텍스트로 돌아온다. 부모는
결국 모든 보고를 읽는다 — 병목이 그대로 남는다.

Rubato의 리드·오너·검증자는 각자 독립된 세션이고, 서로에게 직접 말한다.

- **동료끼리 직접 주고받는다.** 오너와 검증자는 재현 조건, 확인 결과, 수정과 재검증을
  직접 나눈다. 리드를 경유하지 않는다. 막혔을 때도 문제를 가장 잘 아는 세션이 해결
  경로를 이어간다.
- **리드는 필요한 순간에만 깨어난다.** 리드의 프로세스만 팀 전체를 보는 알림을 내고,
  그것도 배치로 모아서 낸다. 메시지마다 리드를 깨우지 않으므로 매번 읽는 맥락과 응답
  횟수를 함께 아낀다.
- **검증은 다른 모델 계열로 한다.** 검증자는 오너와 대화하면서도 독립적으로 판정한다.
  코드를 읽는 것이 아니라 **직접 돌려서** 확인한다. 발견 없음도 유효한 결과다.
- **이해가 쌓인 세션은 이어 쓴다.** 원인을 찾은 오너가 수정과 확인까지 이어간다. 다시
  이해하는 비용을 사지 않는다.
- **팀을 안 만드는 것도 답이다.** 작은 일은 리드 혼자, 또는 단일 세션으로 끝난다. 팀은
  나누는 이득이 설명과 인계, 결과 통합 비용보다 클 때만 만든다.

## 제품 관점을 잃지 않는다

구현이 깊어지면 "이걸 왜 만드는가"가 사라진다. 그래서 제품 판단도 스킬로 꺼내 쓴다.

- **product-framing** — 만들기 전에 사용자, 지금의 대안, 비교 가치, 결과와 실험 범위를
  점검하고 프레임을 동결한다. 만드는 중에도 가치 이탈을 확인한다.
- **product-reframing** — 프레임이 굳어 후보들이 다 비슷해 보일 때, 리서치로 프레임 밖
  후보를 만든다.
- **metaframe** — 첫 해석을 잠정으로 두고, 다음 행동을 바꿀 더 적절한 관점이 있는지 본다.

## 한 세션이 이렇게 흐른다

```
당신 ──대화──▶ 리드
                │  목적과 열어둔 선택을 쥐고, 알아낼 수 있는 것은 먼저 조사한다
                │  "이렇게 이해했고, 이 방향을 권한다"를 당신에게 보여준다
                │
                │  팀이 값을 할 때만 만든다
                ├──▶ 오너      결과 하나를 끝까지. 조사 → 구현 → 디버깅 → 자체 확인
                ├──▶ 오너      독립적으로 진행할 수 있는 다른 결과
                └──▶ 검증자    합의한 기준과 실제 결과를 독립적으로 판정
                │
당신 ◀──판단이 필요한 것만──┘   (실행 중인 일은 오너와 검증자가 직접 주고받는다)
```

## 다른 하네스와 뭐가 다른가

| | 중심 | 당신이 하는 일 |
|---|---|---|
| 채팅 앱 | 대화 하나 | 대화한다. 저장소와 도구 접근은 제한적이다 |
| 단일 세션 CLI (Claude Code, Codex CLI 등) | 한 대화에 전부 | 대화하고, 필요하면 서브에이전트를 띄워 보고를 다시 읽는다 |
| 에이전트 프레임워크 (LangGraph, CrewAI 등) | 사용자가 조립한 그래프 | 역할·흐름·상태를 코드로 정의하고 운영·관측도 직접 한다 |
| **Rubato** | **사용자와 대화하는 리드** | 목적과 우선순위를 이야기한다. 나머지는 리드와 팀이 맡는다 |

터미널에서 돌고, 스킬과 도구를 쓰고, 여러 모델을 고른다는 점은 같다. 다른 것은 **일을
나누고 이어붙이는 책임이 어디에 있느냐**다. 프레임워크는 그 책임을 당신의 코드에 두고,
단일 세션은 당신의 손에 두고, Rubato는 대화를 쥔 리드에게 둔다.

## 설치

**macOS**를 전제한다. Node 24+와 bun 1.4+가 필요하다.

```bash
git clone --branch rubato/base https://github.com/keepitmello/Rubato.git
cd Rubato

./install.sh                # 무엇이 바뀔지 계획만 본다. 파일은 하나도 안 고친다
./install.sh --apply        # 설치하고 모델 왕복까지 확인한다
./install.sh --apply --gui  # 공식 GUI(데스크톱 앱)까지 함께
```

계획을 먼저 읽어라. `--apply`는 항목마다 묻지 않고 계획대로 적용하며, GUI만 따로
물어본다. 끝나면 새 셸을 열거나 안내된 rc 파일을 다시 읽는다.

### 공식 GUI

**`--gui`를 주지 않으면 GUI는 설치되지 않는다.** 대화형 셸에서 `--apply`만 돌리면
물어보지만, 에이전트나 스크립트처럼 표준입력이 터미널이 아닌 자리에서는 묻지 않고
건너뛴다 — 그때는 설치 요약의 "남은 일"에 그 사실이 남는다.

GUI는 [T3 Code](https://github.com/pingdotgg/t3code)를 핀된 커밋으로 받아 Rubato
overlay를 얹고, 화면에 보이는 제공자 이름을 **Rubato**로 맞춘 것이다. 데스크톱 번들은
`~/.rubato/t3-source`에, 앱은 macOS에서 `/Applications/Rubato.app`에 생긴다. 빌드에 몇
분 걸리고 T3 소스를 받으므로 네트워크가 필요하다.

macOS가 아니면 앱 번들 대신 데스크톱 번들만 만들어지고, 터미널에서
`sh harness/t3-integration/start-gui.sh`로 켠다.

### 크레덴셜

설치기는 credential을 복사하거나 새로 만들지 않는다. 연결 상태는 `rubato auth`로 보고,
필요한 계정을 거기서 추가한다. 계정은 공유해도 토큰은 기기마다 자기 것이어야 한다 —
같은 refresh 토큰을 두 기기가 들고 있으면 한쪽이 조용히 죽는다.

## 매일 쓰는 명령

터미널 실행기는 **Rubato CLI**(`rubato`)다. 공식 GUI는 T3다.

```bash
rubato                # Rubato CLI 세션
rubato-gui            # 공식 GUI. 설치 때 --gui 를 고른 경우
rubato auth           # 방향키로 연결 상태 확인·로그인·계정 관리
rubato update         # 변경 내용을 확인하고 업데이트
rubato update --check # 업데이트 유무만 확인
rubato restart        # 도는 것을 새 코드로 올린다 (엔진·remote hub·GUI)
rubato build          # 시스템 프롬프트와 엔진 산출물을 다시 빌드
rubato dispatch <name> [별칭] < brief.md # 비대화 워커. 별칭·모델은 dispatch --help
msearch "<query>"     # 기억 검색
```

## 화면

| | 무엇을 쓰나 |
|---|---|
| 터미널 | Rubato CLI (`rubato`). 대화는 여기서 시작한다 |
| 데스크톱 | **Rubato.app** (macOS). `rubato-gui`와 같은 것을 켠다 |
| 아이폰 | [T3 Code](https://github.com/pingdotgg/t3code) 앱으로 T3 Connect. 맥에서 `rubato-gui`로 연 환경에 붙는다 |

앱이 주기적으로 새 커밋을 확인해 화면 안에서 알리고, 업데이트를 누르면 앱 밖 일회성
작업이 앱을 다시 열어 새 창이 실제로 뜬 것까지 확인한다. 그 경로는 데스크톱 앱에만
있고, Windows·웹·모바일은 위의 터미널 명령을 그대로 쓴다.

## 이 저장소를 고칠 때

철학은 추구하는 방향을, 스킬은 현재의 운영 약속을, 하네스는 그 약속을 실행할 기능을
맡는다. 문서를 고치기 전에 [철학](docs/philosophy/README.md)과 대조하고, 운영 규약은
`harness/skills/`의 스킬 정본에서 고친다. 실제 동작은 코드와 실행 기록으로 확인하고,
가치와 우선순위의 변경은 사용자와 함께 정한다.
